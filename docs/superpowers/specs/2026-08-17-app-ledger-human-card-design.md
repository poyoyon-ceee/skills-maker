# アプリ台帳：人間向け名刺＋直近ダイジェスト

日付: 2026-08-17  
状態: implemented  
範囲: `app-tech-inventory` の出力契約変更。`doc-maint` 本体は改変しない（README 限定の呼び出し方だけ決める）

関連: `D:\vault\アプリ台帳\spec_20260802_アプリ台帳.md`（①棚卸し・③リリースノート。本書は①の人間向け面と、②の読み替え）

## 問題

現行ノート（例: `D:\vault\アプリ台帳\nippo-sec-desk2.md`）は AI 用 YAML が本体で、人間が開いても使えない。

- 概要・できることは frontmatter にあり、本文再掲が禁止されている
- 技術スタックがプラグイン単位まで厚い
- 「直近何が付いた／何を直した」が無い（元spec②未実装）
- README 由来の概要は古いことがある（同例: README 2.2.0 vs 実体 2.8.0）
- `概要要確認: true` と warning を置いても、人間は「技術資料で読めない」で終わり、差分検査をしない

元specの目的（③でフレームワーク更新に気づく）は残す。ただし今の痛みは「このアプリ何で、何ができて、最近何したか」が見えないこと。

## 目標

Obsidian でノートを開いたとき、次が1画面で読める。

1. 何のアプリか（1〜2文）
2. 何ができるか
3. 直近の変化（付いた／直した）
4. 骨格（フレームワーク1行）

技術スタック詳細は frontmatter に残し、③工程の機械層を壊さない。

## 非目標

- ③リリースノート突き合わせの実装
- 元spec②の「fix/revert/workaround から課題推定」
- `doc-maint` の手順・5分類・承認ゲートの変更
- 全アプリに先に `doc-maint` をかける前処理
- Dataview / canvas の全体一覧（後で足してよい。今回は1ノートの型）
- commit 全文の changelog 化
- リポジトリの README を台帳スキルが直接書き換えること

## 設計判断

### 1ノート2層

| 層 | 置き場 | 読む人 |
|----|--------|--------|
| 人間 | 本文 | ヒデ |
| 機械 | frontmatter | AI / 将来の③ |

重複禁止は **技術スタックの本文再掲だけ** に緩める。概要・できることは本文に書いてよい（frontmatter にも残す。③と検索用）。

「綺麗なできることが古い内容を正本に見せる」対策は、人間の気づきに頼らず機械が `未反映` を本文に書く。

### できることの情報源

正本は従来どおり README 系（`README.md` → `README.ja.md` → `docs/README.md` → `PROJECT.md`）。git や実装から「今の機能一覧」を合成して上書きしない。

欠落は `未反映` で明示する。README を直すのはユーザー GO 後の `doc-maint`。

### 直近の窓

1. **正:** git タグ間。使うのは git タグだけ。`package.json` の版数や commit メッセージの `v2.8へ` は区切りにしない
2. **落ち:** タグが0個、1個、または最新タグからマイナー以上の前タグが取れない → 直近90日

タグの取り方:

- 最新タグを `T_new` とする（semver として読めるもの優先。読めないタグは無視）
- `T_old` は、`T_new` より小さい major.minor を持つ最新タグ（パッチ乱発なら 2.8.1 の対は 2.8.0 ではなく 2.7.x）
- その `T_old` が無いなら90日へ落とす

CHANGELOG / GitHub Releases があれば、同じ窓の **文言の正** にする。窓の境界はタグ（または90日）のまま。

### 本文の量（窓によらず固定）

検索窓がタグ間でも90日でも、本文の「直近の変化」は:

- 付いた: 最大3
- 直した: 最大3
- 合計7行（見出し・ラベル除く）

溢れたらユーザー影響が大きい順。残りは `他N件は省略` の1行。

拾う: ユーザー向け `feat` / `fix` / `release:` / 機能名が読めるもの  
落とす: merge、checkout、docs、chore、lockfile、バイナリ追加、版数だけ上げた bump、予防・内部整理

推測で「きっとこう直した」と補完しない。メッセージが雑ならその行は捨てるか `要確認` を付け、小説にしない。

### 未反映

直近窓の **ユーザー向け feat** が「できること」に無いときだけ、`できること` の直下に `未反映:` を書く。

- fix / chore / 予防は未反映にしない
- 文字列完全一致は求めない。同じ機能の言い換えなら未反映にしない
- 迷ったら未反映にしない（直近の変化には書いてよい）。false positive で README 改修に入る方が高い

`概要要確認: true` は従来条件に加え、未反映が1件でもあれば true。本文先頭の warning は技術メモやなく、**この一覧は古い／未反映がある** と1行で書く。見出し「できること」に情報源と時点を付ける（例: `README・2026-03 / アプリは 2.8`）。

### `doc-maint` は後段・バッチ末・承認付き

先に `doc-maint` しない。台帳を全件書いてから、未反映があるアプリだけまとめて1回聞く。

```
未反映 n件: {アプリ名…}
README を直す？
```

- NO / 対象外 → ノートは未反映付きのまま。リポジトリは触らない
- GO → 指定アプリだけ `doc-maint` を呼ぶ。範囲は **README（および README が入口として指す1ファイル）**。docs 全体の維持・統合・移動・削除はしない
- `doc-maint` の監査→承認→適用ゲートは外さない。台帳スキルが README を直接書かない
- 適用後、そのアプリだけ「できること」を再抽出して未反映を消す。スタックと直近は再計算しなくてよい（README だけ変わった場合）

スキルの自動連鎖はしない。バッチ途中で文書改修に入らない。ノート保存が先、GO が後。

## ノート本文の型（固定）

```markdown
# {何のアプリか 1〜2文}

## できること
- …
未反映: …（あるときだけ。複数可）

## 直近の変化（v2.7 → v2.8 など。90日落ちなら「直近90日」）
- 付いた: …
- 直した: …

## 骨格
{フレームワーク＋UI 1行。詳細は frontmatter}
```

本文に書いてよい付加（型の下、短く）:

- 棚卸しメモ（情報源パス、省いた依存）
- ③の一行注記（将来）

本文に書いてはいけないもの:

- 技術スタックの表／プラグイン列挙
- frontmatter の YAML 再掲
- commit ログの生ダンプ

ファイル名と保存先は現行どおり `D:\Vault\アプリ台帳\{アプリ名 or リポジトリ名}.md`。

## frontmatter

現行キーは維持する（`種別` `アプリ名` `概要` `主な機能` `概要情報源` `概要要確認` `技術スタック` `最終更新確認日`）。あるなら `アプリバージョン` `リポジトリパス` も維持。

新規必須キーは足さない。未反映の正は本文。バッチ末の一覧は実行中に集める。セッションが途中で切れても本文の `未反映:` から再開できる。

## 実行フロー

1. 対象リポジトリ確認（現行手順1）
2. 各アプリ: スタック抽出（現行）→ README から概要・できること → タグ判定 → 直近ダイジェスト → 未反映判定 → ノート保存（本文型＋frontmatter）
3. 全件保存後、チャットは要約のみ（YAML 全文再掲しない）
4. 未反映が1件以上なら、対象一覧を出して README 修正の GO を待つ。未反映ゼロならここで終わり
5. GO 分だけ `doc-maint`（README 限定）→ 再抽出 → 当該ノート更新

1アプリ指定でも同じ。手順4の「まとめて」は1件になるだけ。

## 変更ファイル（実装時）

| ファイル | 内容 |
|----------|------|
| `skills-pack/app-tech-inventory/SKILL.md` | 正本。本文型、タグ／90日、7行、未反映、バッチ末ハンドオフ。①-a/①-b に軽量②（ダイジェスト）を含める。③は範囲外のまま |
| `app-tech-inventory/SKILL.md` | pack に追従（ルート複製が残っている間） |
| `skills一覧.md` | 説明を「技術スタック抽出」だけから名刺＋直近に更新 |

`doc-maint/SKILL.md` は変えない。呼び出し側が範囲を指示する。

グローバル反映は既存の promote / install フローに任せる。この仕様の実装コミットに install 実行は含めない。

## 成功条件

1. 新規・更新ノートが上記本文型を持ち、開いて3秒で「何のアプリか」が読める
2. 技術スタック詳細は frontmatter にあり、本文は骨格1行だけ
3. タグがあるアプリはマイナー以上のタグ間、無いアプリは90日でダイジェストされ、本文は7行以内
4. ユーザー向け feat が README 機能一覧に明らかに無いときだけ `未反映` が付く
5. 未反映時もリポジトリは自動で書き換えない。全件保存後の1問で GO したアプリだけ `doc-maint` が走る
6. ③用の `技術スタック` 配列は現行形式を維持する

## 検証

- `nippo-sec-desk2` でドライラン（ファイルを書く前に本文草稿を出す）: できることに README 由来、直近に 2.8 系 feat/fix が7行以内、To Do It / 日報→TODO が未反映になり得ること

## 失敗しやすい点

- 90日やタグ間を「全部出す期間」と誤読する → 上限7行が本体
- 未反映の曖昧マッチで README 改修に入る → 迷ったら付けない
- バッチ途中で `doc-maint` を始める → ノートが揃わない
- 骨格以外のスタックを本文に戻す → また YAML の複製になる
