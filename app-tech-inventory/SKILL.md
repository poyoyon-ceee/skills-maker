# App Tech Inventory (アプリ台帳 棚卸し)

ナレッジ集約システムのアプリ台帳 **①-a 棚卸し + ①-b 保存 + 軽量②（直近ダイジェスト）** を実行する。③（リリースノート突き合わせ）は範囲外。

本人が各アプリの技術・目的・最近の変化を把握していない前提。依存関係ファイル・README・git タグから機械的に取る。README をこのスキルが直接書き換えない。

参照元: `spec_20260802_アプリ台帳.md`（Vault）および `docs/superpowers/specs/2026-08-17-app-ledger-human-card-design.md`

> [!note] 層を分ける
> 技術スタック（manifest）は機械的に正確。概要・できること（README）は古いことがある。直近の変化（git タグ／90日）は README より新しいことがある。本文は人間用の名刺、frontmatter は AI／③用。

## いつ使うか

- 「このアプリ何のフレームワーク使ったっけ」「何のアプリ？何ができる？」
- 複数リポジトリのアプリ台帳バッチ
- 既存台帳ノートを最新の依存関係と直近ダイジェストで更新するとき

## 手順

先に doc-maint しない。ノートを全件保存してから、未反映があるときだけバッチ末に聞く。

### 1. 対象リポジトリを確認する

ユーザーから対象ディレクトリ（複数可）を確認する。指定がなければ、既知のプロジェクトルート配下を探索してよいか確認してから進める。

### 2. 依存関係ファイルを探す

各リポジトリのルート（および主要サブディレクトリ）で以下を探す。見つかったものだけを使う。全部揃っている必要はない。

| ファイル | 抽出対象 | 備考 |
|---------|---------|------|
| `package.json` | JS/TS系: React, Vue, Tauri (via `src-tauri/Cargo.toml`との併用が多い), Electron等 | `dependencies` と `devDependencies` 両方見る |
| `Cargo.toml` | Rust系: Tauri本体, その他crate | `[dependencies]` セクション |
| `requirements.txt` / `pyproject.toml` | Python系: フレームワーク・主要ライブラリ | pyproject.tomlは`[project.dependencies]`や`[tool.poetry.dependencies]` |
| `go.mod` | Go系 | — |
| `Gemfile` | Ruby系 | — |

Tauriアプリは`package.json`（フロント側）と`src-tauri/Cargo.toml`（Rust側）の両方を見ること。どちらか片方だけだと技術スタックが不完全になる。

### 3. バージョンを記録する

各主要依存について、固定バージョンかレンジ指定か（`^1.2.3` 等）をそのまま記録する。正規化・推測はしない。ファイルに書かれた値をそのまま転記する。

### 3.5 README等から概要・できることを抽出する

**探すファイル（優先順）**: `README.md` → `README.ja.md` → `docs/README.md` → 見つからなければ `PROJECT.md`

**抽出する情報**:
- **概要**: アプリが何をするものか、1〜2文（本文の `#` 見出しにも使う）
- **できること / 主な機能**: 箇条書き3〜5個程度（README内の機能一覧・見出しから拾う。無理に数を揃えない）

git や実装から「今の機能一覧」を合成して README を上書きしない。欠落は手順 4.5 の `未反映` で出す。

**古さの扱い**:
- READMEの最終更新が分かる場合（git の commit 日時等）、見出しに時点を付ける（例: `README・2026-03 / アプリは 2.8`）
- 取得できない場合や、依存関係と明らかに矛盾する場合は `概要要確認: true`。技術スタック側を正とし、概要側を無理に整合させない

**READMEが無い／ほぼ空**:
- 概要・できることは「不明（README未整備）」
- エントリーポイントから推測してよいが **「ソースから推測」と明記**し、README由来と混同しない
- 無理に精度を上げようとして時間をかけすぎない

### 4. 「主要」技術だけ抽出する

全依存を列挙すると台帳がノイズだらけになる。優先:

- アプリの骨格を決めるフレームワーク（Tauri, React, Next.js, FastAPI, Flask等）
- ビルド・ランタイムの土台
- 将来の③工程で追跡する価値があるもの

省く: リンター・フォーマッター、極小ユーティリティ（判断に迷ったらユーザーに聞く）

骨格1行は、この「主要」からフレームワーク＋UIだけを短くしたもの。プラグイン列挙は骨格に入れない。

### 4.2 直近ダイジェスト（軽量②）

窓（検索範囲）と本文の量は別。窓が広くても本文は最大 **7行**（見出し・ラベル除く）。

**窓の正: git タグ間。** `package.json` の版数や commit メッセージの `v2.8へ` は区切りにしない。

1. semver として読める git タグを優先。読めないタグは無視
2. 最新を `T_new`
3. `T_old` は `T_new` より小さい **major.minor** を持つ最新タグ（パッチ乱発なら 2.8.1 の対は 2.8.0 ではなく 2.7.x。マイナー以上まで遡る）
4. タグが0個・1個、またはその `T_old` が取れない → **直近90日** に落とす

CHANGELOG / GitHub Releases があれば、同じ窓の **文言の正** にする。窓の境界はタグ（または90日）のまま。

**本文（窓によらず固定）**:
- 付いた: 最大3
- 直した: 最大3
- 合計7行。溢れたらユーザー影響が大きい順。残りは `他N件は省略`

拾う: ユーザー向け `feat` / `fix` / `release:` / 機能名が読めるもの  
落とす: merge、checkout、docs、chore、lockfile、バイナリ追加、版数だけ上げた bump、予防・内部整理

推測で補完しない。メッセージが雑ならその行は捨てるか `要確認`。小説にしない。commit ログの生ダンプは本文に書かない。

### 4.5 未反映

直近窓の **ユーザー向け feat** が「できること」に無いときだけ、`できること` の直下に `未反映:` を書く。

- fix / chore / 予防は未反映にしない
- 文字列完全一致は求めない。同じ機能の言い換えなら未反映にしない
- **迷ったら未反映にしない**（直近の変化には書いてよい）。false positive で README 改修に入る方が高い

未反映が1件でもあれば `概要要確認: true`。本文先頭の warning は「この一覧は古い／未反映がある」と1行。技術メモにしない。

### 5. 出力フォーマット

1アプリ1ノート。既存があれば更新。

**本文＝人間用の名刺。frontmatter＝機械層（③用スタック含む）。** 概要・できることは本文に書いてよい（frontmatter にも残す）。技術スタックの詳細は frontmatter のみ。

#### frontmatter

```yaml
種別: アプリ台帳
アプリ名: {リポジトリ名 or アプリ名}
概要: {1〜2文。README由来。不明なら "不明（README未整備）"}
主な機能:
  - {箇条書き1}
  - {箇条書き2}
概要情報源: {README.md / README.ja.md / PROJECT.md / ソースから推測 / 不明}
概要要確認: {true / false}
技術スタック:
  - name: Tauri
    version: "^2.0.0"
    role: デスクトップアプリフレームワーク
  - name: React
    version: "^18.2.0"
    role: UI
最終更新確認日: {YYYY-MM-DD}
```

- `種別` と `最終更新確認日` のキー名は変更しない
- 各スタック要素に `role` を付ける
- `概要情報源` は必須
- `アプリバージョン` `リポジトリパス` があれば維持。新規必須キーは足さない。未反映の正は本文

#### ノート本文の型（固定）

```markdown
# {何のアプリか 1〜2文}

> [!warning] この一覧は古い／未反映がある
> {あるときだけ。1行}

## できること
（{情報源・時点 / アプリ版}）
- …
未反映: …（あるときだけ。複数可）

## 直近の変化（v2.7 → v2.8 など。90日落ちなら「直近90日」）
- 付いた: …
- 直した: …

## 骨格
{フレームワーク＋UI 1行。詳細は frontmatter}
```

本文に書いてよい付加（型の下、短く）: 棚卸しメモ（情報源パス、省いた依存）、③の一行注記（将来）。

**禁止:** 技術スタックの表／プラグイン列挙、frontmatter の YAML 再掲、commit ログの生ダンプ。

### 5.5 保存先（固定）

- **フォルダ:** `D:\Vault\アプリ台帳\`
- **ファイル名:** `{アプリ名 or リポジトリ名}.md`（既存があれば上書き更新）
- フォルダが無ければ作成してから保存する

ユーザーが別パスを明示した場合のみ、そのパスを優先する。

各アプリ: スタック → README → タグ判定 → ダイジェスト → 未反映 → **保存**。バッチ途中でリポジトリの文書を触らない。

### 6. 全件保存後にユーザーへ提示する

- 抽出できたもの／できなかったものを分けて報告する（要約。YAML 全文再掲はしない）
- 省いた主要判定があれば一言
- 保存先パスを報告する
- **未反映が1件以上**なら、ここで初めてまとめて1回聞く（1アプリ指定でも同じ。件数は1になるだけ）:

```
未反映 n件: {アプリ名…}
README を直す？
```

未反映ゼロならここで終わり。`doc-maint` を提案しない。

#### バッチ末の `doc-maint`（GO 必須）

自動連鎖しない。NO / 対象外 → ノートは未反映付きのまま。リポジトリは触らない。

GO → 指定アプリだけ `doc-maint` を呼ぶ。範囲は **README（および README が入口として指す1ファイル）**。docs 全体の維持・統合・移動・削除はしない。`doc-maint` の監査→承認→適用ゲートは外さない。このスキルが README を直接書かない。

適用後、そのアプリだけ「できること」を再抽出して未反映を消す。スタックと直近は、README だけ変わったなら再計算しなくてよい。

## 注意点

- 専門用語で問い詰めず、抽出結果は素直に見せる
- 推測でバージョンを埋めない。ファイルに無い情報は「不明」
- 概要・機能はスタックより精度が落ちる。`概要情報源` を必ず添える
- 90日やタグ間は検索窓。出す量は7行
- ③は別工程のまま。このスキルは棚卸し・台帳化・直近ダイジェストまで
